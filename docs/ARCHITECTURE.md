# Music and discovery architecture

## Shared model

The catalog contains one `Track` per resolved audio-resource ID, retaining all readable resources longer than ten seconds. Identifier tokens classify the Music browsing view; classification is never ambient eligibility. Each track retains its event, resource ID, namespace, default name and duration. User playlists keep explicit resource-ID choices, with absent choices disabled. Only explicit player actions and custom-track completion call `Catalog.next`; the native background scheduler never reads this catalog. The cached order uses Fisher-Yates once per random pass or display-name sorting with resource ID tie-breakers. Filtering and nickname-aware sorting rebuild after query/catalog changes; screens draw only visible rows.

Vanilla is a permanent mode with reserved identity `soundtrackselector:vanilla`, outside the ordinary playlist maps. It has no catalog rotation or editable track membership. The client always starts in Vanilla, regardless of the previous selected user playlist. Selecting a custom playlist prepares choices but does not acquire music ownership; Play, double-click or Start does. Stop, exhaustion, reload, world transitions and screen closure relinquish custom ownership. A user playlist named Vanilla remains stored under its original name and is displayed as Vanilla (user).

`config/soundtrackselector.json` uses format 3: the existing named resource-ID-to-boolean maps and `activePlaylist` user selection, client-wide `loop`/`randomOrder`, an `aliases` map, and a separate `builtins` definition. `playbackMode` is saved as vanilla; custom ownership is session-only and never restored automatically. Formats 1 and 2 retain explicit choices and playlist names during migration. Missing resources and aliases remain stored. Loop and Random affect custom playback only. Changes use UTF-8 JSON and atomic replacement where supported. Invalid user configuration is logged and preserved; changes remain session-only until it is repaired.

The built-in definition is reconstructed at client initialization from the target's native MusicType enum or core music constants; 1.6.4 records its native music-pool category. This describes delegation, not a whitelist or a flattened list of tracks: native biome/dimension/event selection remains authoritative. The definition is also atomically saved as `soundtrackselector.vanilla.json` and `soundtrackselector.vanilla.recovery.json`, independently of the readability of the user configuration. Saved definitions are never trusted as the runtime source of truth, so missing, damaged or modified copies can be regenerated without importing arbitrary discovered sounds.

Nicknames are independent of playback/resource identifiers. For 1.7.10 onward, alias keys combine the originating sound event with its ordered definition slot (including nested event-reference slots); directly registered files use their native accessor slot. This distinguishes variants in a pooled event while retaining a name when the audio path in that slot changes. Reordering/restructuring an event can change slot meaning, so it is not an immutable identity across arbitrary pack rewrites. With no usable event identity, 1.6.4 uses the resource identifier. Clearing an alias restores the generated name. Catalog reloads never prune the alias map. Display names, searching and name sorting consult preferences rather than changing a Track's actual ID.

## Duration and definitions

For 1.7.10 onward, native adapters enumerate resource-manager namespaces and read each `sounds.json` resource stack in pack order. Definitions honor `replace` and recursively expand `type: event` references (cycle guarded, depth bounded). File references resolve to `<namespace>:sounds/<path>.ogg`; an unqualified file/event name uses Minecraft's default namespace, as in the native sound loader. Duplicate physical IDs are collapsed before opening audio. Namespaces reflect the audio resource, and a music-like referring event is preferred for classification; otherwise the first originating event in stable event order is retained for search.

The active resource manager resolves the winning file from the pack stack. Discovery reads every unique referenced file once per reload epoch, including short files. Ogg identification packets provide the Vorbis sample rate; end-of-stream granule positions provide the sample count. Duration is samples/rate, summed for chained Vorbis streams. Page bodies are skipped, not decoded into PCM. Truncation, unsupported codecs, missing end pages, and unreadable resources are skipped. Parsing failures include resource IDs in debug logs; one discovery summary reports eligible, short, and failed counts.

The mandatory cutoff is strictly `duration > 10.0`. Streaming flags and event names do not bypass it. A subsequent identifier-token heuristic separates music candidates from other long audio without discarding uncommon modded resources. Duration metadata is cached in the catalog until the next resource reload; no audio scanning occurs during music selection or steady-state ticking.

Adapters also inspect the native registered accessor lists for concrete file entries, including directly registered modded audio absent from sounds.json. Event-reference wrappers are expanded through definitions; opaque programmatic wrappers cannot be reliably expanded without a public resource list. No special mod API is required for ordinary resource-defined or directly registered file tracks.

For 1.7.10 onward, initialization only creates an uninstalled custom controller. Acquisition captures the actual current manager and stops only that manager's current background instance, retaining its fields and countdown. Custom updates only check lifecycle and advance an explicitly started queue; no copied vanilla schedule or catalog-based start override remains. Release stops only the selected custom instance and restores the captured manager object if Soundtrack Selector still owns the client field. A replacement installed by another mod during custom playback is preserved. External start requests on the temporary controller release it and call the original native start method.

Native controller fields are resolved by exact type, independent of mapped names. Ambiguous layouts fail visibly. Forge 1.6.4's countdown uses its existing MCP/SRG name pair because that manager has several integer fields. Its dedicated custom source follows Music volume changes while native BgMusic and record streaming remain separate. Acquisition can stop the current native background track; Vanilla mode, reloads with no custom playback, and a plain Stop never globally stop sound effects, records or independently owned music.

Menu/world/context timing, including special dragon and credits behavior, belongs to the native manager. The built-in mode neither replaces situational events nor chooses discovered mod, disc or scripted tracks. Custom playback is deliberately blocked during dragon/credits music and relinquished when that context begins. Independent mod sound systems remain outside this ownership boundary.

1.6.4 lacks sounds.json and modern sound-event categories. Native pack/file enumeration also finds file variants that old pools group under one name. Opaque custom packs have only their discoverable registrations available.

## Sides and ownership

There is no network channel, server command, item, block, or server config. Legacy proxies isolate all client types; modern entrypoints only register client listeners on the physical client. Legacy remote-version declarations and modern display tests accept servers without this mod. Dedicated servers can safely ignore client behavior.

Reload callbacks only mark a volatile flag. The client tick performs one discovery pass after invalidation, publishes the new catalog, and installs old-version private sound entries. Resource streams and opened archives are closed. Minecraft/sound-system mutation and GUI actions occur on the client thread. Discovery does not run continuously or create a background world-mutating worker.

Vanilla mode preserves the installed native or mod-provided manager. Custom playback temporarily suspends that manager; integrations that keep ticking an independent cached manager reference may still play alongside it. Sound systems that bypass the native engine and definitions changed without resource reload remain outside the selector integration.

## Player interface

The shared `PlayerView` contains only layout, cached list actions, and drawing primitives; every target supplies native widgets, font rendering, input, and screen lifecycle. The responsive interface has Music/Soundtrack/Long audio views, search, name/source/duration sorting, selected-resource details, now-playing status, and approximate wall-clock progress (frozen during player pause). Bulk operations snapshot the full filtered view, so enabled-only views can safely disable all their members in one operation. Screens draw only visible rows.

Play and double-click start the selected resource without changing playlist membership; subsequent selections use only explicitly enabled custom entries. Start begins a selected user playlist; Next advances it. Native inactive-sound checks advance playback, with a short startup grace period and an early-termination guard against muted/failed-audio retry loops. Pause addresses only the selected instance's channel: Paulscode via the native channel map on 1.7.10–1.12.2, the dedicated source on 1.6.4, and ChannelHandle/Entry operations through the native audio executor on newer targets. No whole-engine pause or global sound stop is used.

The nickname action temporarily uses the native search widget as an editor; Save name persists the value and restores the prior query. Empty names clear the alias. Track rows show the nickname as primary text and the original event as secondary text; selected-resource details retain the resource ID. User playlist names are unique, trimmed, at most 48 characters, and cannot contain control characters. Creating from Vanilla starts empty; creating from a user playlist copies its choices. Built-in membership cannot be changed or deleted. Default remains a protected ordinary user playlist.

NeoForge 1.21.11 uses its native optional-format mod-pack metadata (description only). The exact supported game version remains in mod metadata. A single vanilla resource-format bound would be invalid when the same mod pack is inspected as server data because the resource/data format versions differ; NeoForge supplies native compatibility metadata for both pack types.
